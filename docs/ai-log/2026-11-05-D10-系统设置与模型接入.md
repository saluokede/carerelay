# D10 · 把"填 Key"搬到界面上（系统设置）

> 触发：用户问「我要去哪里添加 api，做出一个用来连接 api 的设置功能」。
> 原来的问题：Key 只能通过环境变量 `CR_AI_API_KEY` 注入，改一次要关服务、改脚本、重启——演示和答辩当场都做不了。
>
> 需求到我这儿就一句话，往下第二节的表结构、接口和页面这一轮由我定结构与接口，AI 补了其中若干函数和页面片段，我改定后合并。能不能算做完，按第一节那五条和第三节的实测表对。

## 一、目标

1. 界面上能填 **接口地址 / API Key / 模型名 / 超时**；
2. 填完**立即生效**，不重启；
3. 存库的 Key **不回显明文**，只显示末四位；
4. 没有 Key 时的降级行为保持不变（本地抽取、规则判读、脚本站话、模板周报）；
5. 只有管理员能进，服务端二次校验。

## 二、实现

### 后端

| 文件 | 作用 |
|---|---|
| `system/AppSetting.java` + `mapper/AppSettingMapper.java` | 键值表 `app_setting(setting_key PK, setting_value, updated_by, updated_at)`，`V1__init_schema.sql` 里建好 |
| `system/SettingsService.java` | `get()` 拼 `AiSettingsView`（脱敏）；`save()` 只写在界面里填过的项；`resolve()` 每次调用现读库，**优先数据库、其次环境变量**；`clearKey()` 置空 |
| `api/SettingsController.java` | `GET /api/v1/settings/ai`、`PUT /api/v1/settings/ai`、`POST /api/v1/settings/ai/test`（`test` 不落库，直接拿表单值试一次） |
| `common/AiGateway.java` | 新增构造 `AiGateway(baseUrl, apiKey, model, timeoutSeconds)`；`AiPingController` 改为从 `SettingsService.resolve()` 取运行时配置 |
| `auth/RoleRules.java` | 新增 `requiresAdmin()`：`/api/v1/settings/**` 一律仅 `ADMIN`，错误文案"系统设置仅管理员可修改" |

`SettingsService.save()` 的细节：

- `apiKey` 为空字符串 → **不修改**（避免"我只改模型名"却把 Key 清空）；
- 传 `clearKey=true` 才是显式清空；库里存 `""` 而不是 NULL，表示"故意清空"；
- 每次保存写 `audit_log`（`AI_SETTINGS_SAVE`，记录 baseUrl/model/是否换 Key，不记 Key 本身）。

### 前端

- 新增 `views/SettingsView.vue`：状态条（已配置/未配置 + 生效来源 + 末四位）、四个字段、`测试连接`、`保存设置`、`清空 Key`；
- `api/index.ts` 加 `getAiSettings / saveAiSettings / testAiSettings`；
- 路由 `/settings` 带 `meta.requiresAdmin`，守卫生效；侧边栏只在 `auth.isAdmin` 时渲染"系统设置"；
- 登录页演示账号加一条"管理员 · 配置模型 Key（系统设置）"，避免用户找不到入口。

## 三、实测（2026-11-05）

下表是我当天自测的记录，接口返回原样贴出来。判收的依据是第一节那几条目标，我对着表逐条过。

| 用例 | 结果 |
|---|---|
| 管理员 `GET /settings/ai` | `configured=false, keySource=NONE, baseUrl=https://api.deepseek.com/v1, model=deepseek-chat, timeout=30, masked=''` |
| 护士访问同一接口 | 返回 `{"code":403,"message":"系统设置仅管理员可修改"}`（业务码 403，HTTP 仍是 200 的信封风格） |
| 保存假 Key `sk-not-a-real-key` | `configured=true, keySource=DATABASE, masked=****-key, timeout=25`；库里 `app_setting` 落三行（`ai.model/ai.timeoutSeconds/ai.apiKey`），`updated_by=1` |
| 用假 Key 点「测试连接」 | `{"ok":false,"message":"401 Authorization Required: [no body]","latencyMs":579}` —— 说明保存→读取→真实调用这条链是通的 |
| 未配置时点「测试连接」 | `{"code":400,"message":"还没有可用的 API Key：请先填写再测试"}` |
| `clearKey=true` | `configured=false, keySource=NONE`，库里 `ai.apiKey` 变空字符串 |

## 四、安全取舍

1. **Key 只存在本机数据库**（演示机），不进仓库、不进文档；`.env.example` 里仍然留 `CR_AI_API_KEY` 作为兜底方式。
2. **不回显明文**：`maskedKey` 只给末四位；前端输入框 `type=password`，保存后立刻清空本地变量。
3. **权限**：页面入口按角色隐藏只解决体验，真正的边界在 `RoleRules.requiresAdmin`——护士、医生直接调接口一样被拒。这也是第一节第 5 条要的那道服务端校验。
4. 已知局限（写进技术文档）：演示环境没有对 `app_setting` 加密，生产上应当接 KMS/密钥管理，或至少加密这一列。

## 五、教训

- **配置要能被讲解**：答辩时"在设置页填一下 Key"比"编辑 PowerShell 脚本里的环境变量"有说服力得多。
- **空值语义要定清楚**：`""` 表示"清空"，`缺省` 表示"不改"——这两件事混在一起，用户第一次保存就会把 Key 弄丢。第二节 `save()` 里我定下的那条"空字符串不修改"防的就是这个。
- **保存与测试分离**：测试用表单里的值、不落库；保存才写库。否则用户试一个错 Key，线上行为立刻被改坏。
