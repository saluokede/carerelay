# D3 随访环：随访会话、对话推进与结束摘要

- 日期：2026-11-04
- 涉及模块：followup（随访会话 / 对话推进 / 结束摘要与红旗升级）、api（FollowupController）、db（V2 迁移）、prompts（followup_chat / followup_summarize）
- 本轮模型调用次数：**0**（本机未配置 `CR_AI_API_KEY`，全部走规则/脚本兜底，`mode=SCRIPT`、`_source=RULE`）

## 一、这一轮要解决的问题

交接环和计划做完了，老人拿到 30 天的任务清单，执行环能打卡判读。但还有一个空档：**一周后谁来问？问了以后的话记在哪？**

- 护士不可能每天打三个电话；家属只报"挺好的"，坏消息就沉下去了。
- 电话随访最容易丢的东西不是内容，是**结构**：一句话里既有症状、又有情绪、还有诉求，散在聊天记录里没法统计。
- 打完电话最怕"记在纸上就过去了"，红旗症状没有触发任何动作。

所以这一环的目标是：**按计划的随访间隔排期 → 按固定顺序问完六件事 → 结束自动生成结构化记录 → 红旗症状当场升级成预警和工单。**

## 二、AI 在这轮的具体位置与边界

这一轮模型调用是 0 次：本机没配 `CR_AI_API_KEY`，六个问题、规则摘要、红旗词表全得由 AI 写成代码兜底，没有模型可用。所以动代码之前先把分工定死——左列是能交给 AI 的，右列是人工和代码必须守住的：

| 环节 | AI 做什么 | 人工/代码守住什么 |
| --- | --- | --- |
| 排期 | 不参与 | 间隔取自已签发计划的 `followup_json.interval_days`（默认 7 天），代码排期 |
| 对话推进 | 有 Key：`followup_chat.v1` 带老人档案、出院诊断、已问内容，一次只问一个问题，口语化 | 无 Key：脚本六问按顺序推进，问题固定、不离题 |
| 结束摘要 | 有 Key：`followup_summarize.v1` 输出 JSON（症状/用药/跌倒/伤口情绪/需求/红旗/三行摘要） | 无 Key：按"第几问对应哪一段回答"做规则抽取；输出必须过 JSON 校验，不合格就回退规则摘要 |
| 红旗升级 | 不参与 | 词表命中即 `red_flag=true` → 建 HIGH 预警 + 工单（来源 FOLLOWUP），护士必须处置 |
| 是否改计划 | 不参与 | 随访记录只做输入，改计划仍是护士在计划页签发新版本 |

## 三、实际跑出来的东西（2026-11-04，后端 8081，库 `carerelay@3307`）

脚本六问：症状 → 用药 → 跌倒 → 伤口 → 饮食睡眠情绪 → 需求。

下面两段都是脚本模式下跑的，一段把问题说全，一段几乎全盘否认，规则抽取的两头都在里面。

会话 A（陈美英，脚本模式，回答里带着"摔倒过 + 伤口红 + 睡不好"）：

| 轮次 | 家属说 | 助手下一句 | questionIndex |
| --- | --- | --- | --- |
| start | — | 开场白 + "这几天有没有胸闷、胸痛，或者喘不上气的时候？" | 1 |
| 1 | 没有胸闷胸痛，就是走路有点喘 | "药都按时吃了吗？有没有漏服或者自己停过？" | 2 |
| 2 | 药都按时吃了，没漏 | "这一周有没有摔倒，或者起身发晕、差点摔倒？" | 3 |
| 3 | 上周起夜时差点摔倒，扶住墙了 | "伤口换药还顺利吗？有没有红肿、渗液或者发热？" | 4 |
| 4 | 伤口有点红，换药时有点疼 | "饭吃得下吗，晚上睡得好不好？心情怎么样？" | 5 |
| 5 | 饭吃得下，晚上总睡不着，心里烦 | "还有没有想让我转告护士的事，比如换药、开药或者上门？" | 6 |
| 6 | 想让护士上门看看伤口 | 收尾语，`ended=true` | 6 |

结束时生成 `followup_record`：`red_flag=true`（走到"摔倒"）→ 自动建 HIGH 预警 + PENDING 工单（`source=FOLLOWUP`），护士在预警页处置。

会话 B（王秀兰，六问全部答"没有/还好"）：

```
主诉：喘
需注意：暂无红旗，关注依从性
下一步：安排上门
```

`falls.happened=false`（"没摔倒，就是起夜有点头晕"→ 只记录头晕，不算跌倒事件）、`wound.issue=false`（"不红不肿"是否定）、`medication=按时`、`mood=低落`、`needs=[上门]`、`red_flag=false` → 不建预警。

## 四、这轮改过的东西（都是"规则说错了"而不是"数据编错了"）

六条都是实跑之后改的，共同点是规则和状态机写错了，不是测试数据编错。需要拍板边界的两条（第 4、5 条）由我给结论——只认"摔/跌"，轻微疼痛不进预警——落到代码由 AI 改。

1. **问题推进 off-by-one**：首版 start 之后 questionIndex=1，用户答完第一题直接跳到第 3 题（跳过"用药"），第 5 轮就把收尾语发出来。改成"questionIndex = 已问过几题：先问第 asked 题、再 +1"，六轮问满才结束。
2. **同日排期复用了已完成的会话**：旧逻辑是同老人同一天只要有会话就复用，结果一点"开始随访"直接拿到一个问完的会话、每轮都回收尾语。改成只复用 `status=PLANNED` 且 `transcript_json` 为空的会话。
3. **规则摘要串味**：旧版把整段对话丢进关键词匹配，结果"摔倒/渗液/发热"被当成"症状"列进 symptoms，而且"没有胸闷"被判成有胸闷。改成按"第几问对应哪一段回答"逐项抽取 + 前置否定词判断（前面 6 个字带 没有/没/无/不/未 就不算提到），症状只从第一问里取，红旗词单独判。
4. **跌倒与头晕分开**：`falls.happened` 只认"摔/跌"，"头晕"写进 detail 不升级成跌倒事件。
5. **伤口问题收窄**：只把红肿/渗液/渗血/发红/流脓算伤口问题；"换药时有点疼"只进 detail，避免轻微疼痛触发预警。
6. **elderName 为空**：列表和 due 接口原本传 null 老人对象，随访列表看不到名字，改成按 elderId 回查。

改完之后验收就看会话 A、B：A 走到"摔倒"必须出 `red_flag=true`、自动建 HIGH 预警和 PENDING 工单，B 必须停在 `red_flag=false`、不建单。

## 五、踩过的坑

- `Start-Process` 起的 java 会在 `pwsh` 命令结束时被回收，必须用后台作业拉起后端。
- 旧 java 进程占着 jar 会让 `mvn package` 报 `Unable to rename ...jar`；`Get-CimInstance Win32_Process` 被沙箱拒绝，改用 `Get-Process java` 看 `Path`。
- MySQL 客户端短参数 `-h127.0.0.1` 会被拆成 `-h 127`，必须写 `--host=127.0.0.1`。
- 控制台中文乱码只是显示层（UTF-8 被按 GBK 打印），接口和库里都正常。
