## 四、评委可能问的十个问题

**Q1：这和医院的随访系统有什么不一样？**
医院系统管"院内"，出院那一刻就断了。我们接的是**交接点之后**：把出院小结翻译成社区和家属能执行的动作，
并且用打卡和对话持续采集，而不是等到复诊。差异化的不是功能多少，是**交接这段谁负责**。

**Q2：AI 会不会乱开药？**
不会，因为模型没有这条通路。剂量只从出院小结里抽取，抽不到就进 `missing_fields` 让人补；
任务清单是代码按药单逐条展开的；计划必须护士签发才生效。

**Q3：模型判断错了怎么办？**
三层兜底：① 数值类完全不经过模型，由 `VitalRules` 代码判定，规则码可追溯；
② 文本类判读失败降级关键词表；③ 关键结论（红旗、计划）都有人工确认节点，且 `ai_request` 留了原始输入输出，
事后可复核。我们宁可"漏报后人工补"，也不让模型在没有标注数据时下诊断结论。

**Q4：为什么不用 LangChain / Spring AI？**
只用 chat 一种能力。自研 200 行网关换来三件事：每次调用都落库、降级路径可控、不引入版本漂移。
引入框架在这个规模下是负担，不是加分。

**Q5：你们的评分卡凭什么可信？**
分数是代码算的，9 个因子加总，任何评委会后拿一位老人重算都能得到同一个数。
模型只负责把因子翻译成人话，不参与打分。

**Q6：随访 Agent 和老人在微信里聊天有什么区别？**
它有**任务**：六件事必须问完，问完才生成结构化记录；有**红线**：命中胸痛、呼吸困难、摔倒等词，
立刻升级高危预警 + 工单，不等对话结束；有**留痕**：每轮问答进 `followup_session`，可回溯。

**Q7：数据从哪来？真实场景怎么落地？**
演示数据是虚构的四位老人。落地路径：先接社区已有的出院小结（HIS 导出或护工拍照转录），
风险评分卡与随访排期不依赖模型即可运行——这正是我们做降级设计的原因。

**Q8：效果怎么衡量？**
系统内：30 天结局报告（再入院、预警次数、任务完成率、风险变化）。
系统外：与社区对照，比较 30 天再入院率与随访完成率。目前只有前者，后者需要真实部署。

**Q9：这套东西的边界在哪？**
不做诊断、不做处方、不做急救决策。照片只排队给护士看，不送模型做诊断——
在没有标注数据时，这么做会引入比收益更大的风险。

**Q10：3 天做完，是不是靠 AI 堆出来的？**
是"用 AI 提效"，不是"让 AI 决定"。过程留痕在 `docs/ai-log/`：每轮写清输入、AI 产出、人工改了什么、怎么验证。
比如周报那个缺陷——界面正常、库里 `FAILED`——是我对着 `ai_request` 一条条核对才发现的。
AI 交上来的页面显示正常，这类"跑得通、但数据对不上"的问题它不会自己提出来。

## 附：Git 历史怎么一键建起来（等主人点头再跑）

赛事要求"完整的、细粒度的 Git 提交历史，禁止一次性提交"。仓库目前还没有 `.git`，
`scripts/git-bootstrap.ps1` 是 AI 写好、在副本上**演练过一遍**的：17 次提交、161 个跟踪文件、
工作树干净、没有把 `node_modules / target / dist / .tmp` 带进历史。演练通过只说明脚本能用，
真跑起来要等我点头。

```powershell
# 在仓库根目录执行（只做本地 init/add/commit，不 push）
.\scripts\git-bootstrap.ps1     # Git Bash 或 pwsh
powershell -ExecutionPolicy Bypass -File .\scripts\git-bootstrap.ps1   # 被"未数字签名"拦住时
```

拆分的 17 条提交对应 17 个可复述的功能单元（骨架 → 公共层 → 鉴权 → 建库 → 档案 → 抽取 →
评分 → 计划 → 打卡 → 预警 → 随访 → 复盘 → 前端 → 测试 → 脚本 → 文档 → 兜底），
每条都能在答辩时说明"这一次提交解决了什么问题"。

提交身份写在仓库本地配置里（`CareRelay Team <carerelay@example.com>`），换成自己的名字和邮箱即可，
不会改动全局 git 配置。
