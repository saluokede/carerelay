## 1. 作品概述

**医养接力站**（CareRelay）是一个面向出院老人的智能康复照护与社区随访系统。

它把一次出院当作一次**交接**：医院把老人交给社区与家庭，中间是 30 天最容易掉链子的空档。
四个环把这段空档接起来：

| 环 | 触发时点 | 系统做什么 | 谁拍板 |
|---|---|---|---|
| 交接环 | 出院 24 小时内 | 出院小结 → 结构化档案 → 风险评分卡 → 30 天照护计划草案 → 每日任务展开 | 社区护士签发 |
| 执行环 | 每天 | 任务打卡（数值/文字/照片），依从性追踪，异常判读与预警 | 规则命中即预警 |
| 随访环 | 按风险分层的间隔 | 六问对话 Agent 采集症状，生成结构化随访记录，红旗升级工单 | 家庭医生处置 |
| 复盘环 | 每周 / 出院第 30 天 | 双版本周报（家属白话版 / 医护要点版）、30 天结局、护士台总览 | 护士确认 |

**一句话**：出院不是终点，是接力的交接点；AI 不替代医生护士，只负责让交接棒不掉。

## 2. 问题与依据

### 2.1 数据背景

- 我国 60 岁以上人口超 3.2 亿（2025 年末占 23.0%），失能老人约 3600 万、失智约 1700 万。
- 老年患者 30 天再入院率的国际参考区间为 **11%–23%**；相当一部分可通过出院后规范随访避免。
- **39.1%** 的患者存在至少一种用药偏差，其中**超过 60%** 发生在医院—家庭护理过渡阶段。
- 政策侧：「互联网+护理服务」2019 年六省市试点、2020 年国卫办 985 号文推进，社区承接出院后照护已是明确方向。

### 2.2 痛点拆解（不是"没有工具"）

| 痛点 | 现场表现 | 本系统的回应 |
|---|---|---|
| 出院小结是自由文本 | 社区护士看不懂缩写、拿不到药单 | 结构化抽取 + `missing_fields` 显式暴露缺口 |
| 无法判断"谁最该先看" | 所有出院老人一样对待 | 代码算分的风险评分卡，分数可复算、可解释 |
| 家属听不懂医嘱 | 依从性差、用药错误 | 计划拆成"今天几点做什么"，打卡一次一步 |
| 异常发现太晚 | 等复诊才知道血压失控 | 每日打卡判读 + 分层预警 + 自动工单 |
| 随访靠电话逐个问 | 护士时间被低效占用 | 对话 Agent 先问、先筛，人只看红旗 |
| 效果无法量化 | 汇报时只有"我们随访了 N 次" | 30 天结局报告：再入院、预警数、完成率 |

## 3. 用户与权限

| 角色 | 能看到什么 | 能做什么 |
|---|---|---|
| 社区护士（NURSE） | 工作台、在管老人、预警与工单 | 建档、抽取、评估、生成并**签发**计划、建随访排期、处置工单 |
| 家庭医生（DOCTOR） | 同上 + 临床版周报 | 处置工单、查看结局报告 |
| 家属（FAMILY） | 今日任务、本周复盘（白话版） | 打卡、记录一句症状、提交照片 |
| 管理员（ADMIN） | 账号与审计 | 演示环境未开放自助注册 |

登录用 JWT（`cr.jwt`，默认 72 小时），服务端 `AuthInterceptor` 校验；所有写操作落
`audit_log`（动作、对象、对象 id、操作人、时间）。

**权限在服务端校验，不靠前端藏按钮**。`auth/RoleRules` 按"方法 + 路径"拦截会改变照护结论的写操作：
建档、抽取、评估、生成/签发计划、关闭预警、处置工单、发起随访、生成周报、读护士台总览。
家属账号访问这些接口一律 403，但仍可读今日任务、提交打卡、查看周报——
"家属能做什么"由服务端定义，`RoleRulesTest` 有 8 个用例专门守这条线（含"路径带 query 不能绕过"）。

## 4. 总体架构

```
Browser (Vue 3 + TS, hand-written CSS)
   │  /api/v1/**  (JWT)
   ▼
Spring Boot 3.3 / Java 21
   ├── api/        控制器（10 组 REST）
   ├── discharge/  抽取（EXTRACT 场景）
   ├── risk/       评分卡（纯代码）+ 解释（RISK_EXPLAIN）
   ├── plan/       计划草案（PLAN_GENERATE）+ 任务展开（纯代码）+ 签发
   ├── checkin/    打卡（VitalRules 纯代码 / CHECKIN_JUDGE）
   ├── followup/   随访 Agent（FOLLOWUP_CHAT / FOLLOWUP_SUMMARY）
   ├── report/     周报与结局（REPORT_FAMILY / REPORT_CLINICAL）
   ├── ai/         AiGateway（OpenAI 兼容）+ AiCallService（校验/重试/降级/留痕）
   └── common/     ApiResult、异常、审计、JsonText
   │
   ▼
MySQL 8 (Flyway V1/V2, 17 张表) + 提示词外置 resources/prompts/*.md
   │
   ▼
LLM：OpenAI 兼容协议（默认 DeepSeek deepseek-chat）
```

### 4.1 关键取舍

1. **不用 Spring AI / LangChain**：只用到 chat 一种能力，自研 `AiGateway` 200 行即可，
   换来"每一次调用都被记录"的确定性，也不引入版本漂移。
2. **提示词外置为独立文件**（`resources/prompts/*.v1.md`）：便于在 Git 里看到提示词的每一次修改（评审可查），并且可以标注版本号（`*.v1.md`）。
3. **不引前端组件库**：首版由 AI 起手把 Element Plus 全量引了进来，包 1,064 kB / gzip 350 kB，页面零使用；
   这条由我否掉，改为手写 CSS，构建落到 **109 kB / gzip 42 kB**。
4. **JSON 列按字符串存取**：模型原始输出可能不是合法 JSON，保留原文比强转更有利于事后复盘。

## 6. 四个环的实现

### 6.1 交接环

**抽取**（`discharge/DischargeService`，场景 `EXTRACT`）

1. 提示词 `prompts/extract_discharge.v1.md` 规定 12 段 JSON Schema（诊断、手术、用药、管路、伤口、饮食、活动限制、复诊、红线、缺失字段、逐字段置信度）。
2. 模型返回后 `JsonText.parse` 校验：字段缺失 → 补默认值；**JSON 不合法 → 重试一次**；再失败 → 降级为 `extract_status=MANUAL`，前端转手工录入，绝不编造。
3. 落 `discharge_record.data_json` + `missing_fields` + `confidences`；每次调用写 `ai_request`。

**评分**（`risk/RiskScoringService`，**纯代码**，不调用模型）

| 因子 | 分值 | 判定来源 |
|---|---|---|
| 年龄 ≥85 / ≥75 | 2 / 1 | 生日 |
| 独居 | 2 | living_status |
| 无照护人 | 1 | caregiver 字段 |
| 多重用药 ≥6 / ≥4 | 2 / 1 | 药单条数 |
| 留置管路 | 2 | 管路 |
| 有伤口 | 1 | 伤口 |
| 认知障碍诊断 | 2 | 诊断关键词 |
| **独居且有伤口或管路（叠加）** | **2** | 两项同时成立 |

阈值：≥6 高危、≥3 中危、其余低危。**分数可复算**——评委拿任何一位老人重算，结果一致。
模型只负责 `RISK_EXPLAIN`：把因子翻译成一句人话，失败时用模板兜底。

> 这条"叠加项"是评审中值得讲的细节：初版规则下，84 岁独居、带伤口、5 种药的李国强只有 5 分（中危）。
> 我按现场情况判"独居且要自己换药"应属高危，否掉了这个结果，让 AI 改规则表加 `HOME_GAP +2`——**改的是规则，不是数据。**

**计划**（`plan/PlanService`，场景 `PLAN_GENERATE`）

1. 先确保有评分（无则自动评估），再请模型出草案：目标、红线、随访间隔与渠道、AI 总结。
2. **任务由代码展开**：`buildTasks` 遍历药单，每个药按频次生成 MED 任务（`qn`/晚 → EVENING），
   另加每日 VITAL（血压）、有活动限制加 REHAB、有伤口加 WOUND；窗口 7 天 × 30 天计划。
   模型没有任何"加一条药"的通道。
3. 护士点「签发」：`DRAFT → ISSUED`，写 `issued_by`/`issued_at`，落 `PLAN_GENERATE`/`PLAN_ISSUE` 审计。

### 6.2 执行环

**判读分流**（`checkin/CheckinService.submit`）

| 输入 | 判读器 | 产出 |
|---|---|---|
| 数值（BP/GLU/TEMP/SPO2/WEIGHT） | `VitalRules`（纯代码） | `judge_source=RULE`，规则码如 `BP_CRITICAL_180_110` |
| 文字描述 | 模型（`CHECKIN_JUDGE`）→ 失败降级关键词 | `judge_source=MODEL` / `KEYWORD_*` |
| 照片 | 排队目视（`PHOTO_PENDING`） | 待护士查看，不臆造结论 |
| 无内容 | `CHECKED` | 仅记完成 |

阈值（节选）：血压 ≥180/110 高危、≥160/100 中危、<90 高危、≥140/90 中危；
血糖 ≥16.7 或 <3.9 高危、≥11.1 中危；体温 ≥38.5 高危；血氧 <92 高危、<95 中危。

**闭环**：异常 → `alert_event`；高危 → 同时建 `ticket`；护士处置 → `TICKET_HANDLE` / `ALERT_CLOSE` 审计。

### 6.3 随访环

**排期**（`schedule`）：读最新 ISSUED 计划的 `followup_json.interval_days`（缺省 7 天），同日去重；
高风险老人的计划通常给出 3 天间隔——这就是"按风险分层随访"的落地。

**对话**（`FOLLOWUP_CHAT`）：六问固定顺序（症状 → 用药 → 跌倒 → 伤口管路 → 饮食睡眠情绪 → 需求），
一次只问一件；`question_index` 语义为"已问过几题"，避免跳题；六问结束写 `[END]`。
模型不可用时走脚本模式（`mode=SCRIPT`），业务不中断。

**结构化**（`FOLLOWUP_SUMMARY`）：输出 `symptoms/medication/falls/wound/mood/needs/red_flag/summary`；
模型失败时 `ruleSummary` 按"第几问=哪段回答"逐项抽取，**否定词处理**（`没有摔倒`、`无红肿`）避免误报。

**升级**：`red_flag=true` 或命中红旗词表 → 自动建 HIGH 预警 + PENDING 工单。

### 6.4 复盘环

`report/ReportService.snapshot(elderId, start, end)` 汇总：任务完成率与逐日趋势、打卡与异常数、
预警（高/未关闭）、工单、随访红旗、风险分变化、各体征最近值。

- **家属版**（`REPORT_FAMILY`）：白话 3–4 句，禁术语，不下建议。
- **临床版**（`REPORT_CLINICAL`）：markdown 四段（概况 / 指标 / 预警与随访 / 需关注），含完成率表格。
- **30 天结局**（`outcome`）：再入院、预警次数、完成率、风险变化，直接从库计算。
- **护士台总览**（`overview`）：风险分布、待随访、未关闭预警、待处置工单、平均完成度、每位老人一行。

## 7. AI 工程规范（本项目的差异化主张）

### 7.1 三条底线

1. **数值归代码，语言归模型**：评分、阈值、剂量、任务展开一律代码计算；模型只做抽取、解释、组织语言。
2. **结构化优先**：所有模型输出过校验（JSON 解析 + 必填字段），失败重试一次，再失败降级模板并显式标注 `mode=LOCAL`。
3. **人在环**：计划必须护士签发；模型不改药、不下诊断；照片不外推到模型做诊断。

### 7.2 提示词管理

- 外置为 `backend/src/main/resources/prompts/*.v1.md`，8 个场景：`EXTRACT`、`RISK_EXPLAIN`、
  `PLAN_GENERATE`、`CHECKIN_JUDGE`、`FOLLOWUP_CHAT`、`FOLLOWUP_SUMMARY`、`REPORT_FAMILY`、`REPORT_CLINICAL`。
- 每个提示词写明：角色、输入数据、输出 JSON 结构、禁止事项（不诊断、不给剂量、不编造缺失项）。
- 修改提示词会出现在 Git diff 里，属于可被评审的"工程痕迹"。

### 7.3 调用留痕与可观测性

`ai_request` 每行记录：`scene`、`mode`、`model`、`input_json`、`output_json`、`status`、`latency_ms`、`adopted`。

这份表有实际用途——**周报缺陷就是靠它发现的**：`REPORT_FAMILY` 显示 `FAILED / latency=0 / input_json 空`，
而界面上"看起来正常"。AI 顺着这条记录往下挖，根因链是五步：`JsonText.of()` 用默认 `ObjectMapper` 序列化含 `LocalDate` 的入参时抛异常 →
被 catch 吞掉返回 null → `Map.of(k, null)` 抛 NPE → 上层静默回退模板，但对外仍报 `mode=MODEL`。

修复三处：
1. `ObjectMapper` 注册 `JavaTimeModule` 并关闭 `WRITE_DATES_AS_TIMESTAMPS`；
2. `AiCallService` 增加两道前置校验，空系统提示词/空入参直接抛**带场景名**的异常，不再静默；
3. 补 15 个单元测试（`JsonTextTest` 4 个、`VitalRulesTest` 7 个、`JwtServiceTest` 4 个）。

修后复测：`REPORT_FAMILY SUCCESS 1482ms`、`REPORT_CLINICAL SUCCESS 2976ms`（均真实模型）。

### 7.4 降级矩阵

| 场景 | 模型不可用时的行为 | 用户看到 |
|---|---|---|
| EXTRACT | 不生成结构化结果 | `extract_status=MANUAL` + 提示"请手工填写" |
| RISK_EXPLAIN | 模板句（因子拼接） | 解释仍可读 |
| PLAN_GENERATE | 模板草案（目标/红线/随访默认值） | 可签发，任务照常展开 |
| CHECKIN_JUDGE | 关键词表 + 红旗组合式匹配 | `judge_source=KEYWORD_*` |
| FOLLOWUP_CHAT | 脚本模式（固定六问） | `mode=SCRIPT` |
| FOLLOWUP_SUMMARY | 规则摘要 | `red_flag` 仍按词表判定 |
| REPORT_* | 模板周报（数字仍真实） | 标注本地模式 |

## 8. 安全、隐私与合规

- **不诊断、不处方**：提示词与代码双重约束；剂量字段只允许来自出院小结原文。
- **最小化采集**：只存照护必需信息；演示数据全部为虚构人物（王秀兰/李国强/陈美英/赵德海）。
- **密钥管理**：Key 只经环境变量注入（`CR_AI_API_KEY`），仓库只有 `.env.example`；
  日志与文档不打印 Key；`.gitignore` 覆盖 `.env`、`.tmp/`、`uploads/`。
- **图片策略**：照片不出系统外，仅排队给护士目视（不送模型做诊断）。
- **审计**：所有写操作与 AI 采纳情况可追溯。
- **模型凭据**：Key 存在本机 `app_setting`，界面上只回显末四位，审计日志不记录 Key，保存/清空均留痕；演示环境未做列加密，生产应接密钥托管。

| 缺陷回归 | 打卡 `kind` 缺失、周报静默降级、随访气泡字段不一致、列表漏 `transcript`、家属端空编号无提示、出院日期排序、建档表单预填、人工填写缺闭环 | 均已修复并复测 |

**三个真实的缺陷（都是"真跑才暴露的"）**：
1. 血压 172/104 被静默记成"已完成"——客户端只给 `valueJson` 不给 `kind`，服务端判读分支没进。已改为从载荷读 `kind`。
2. 周报静默回退模板（见 7.3）。
3. 随访 Agent 的 `question_index` 跳题（问答错位一题），已改为"先问第 asked 题再 +1"。
4. 随访页面气泡只有标签没有内容：后端存 `{role:"assistant", content}`，前端按 `{role:"agent", text}` 渲染。接口断言全绿时这一页其实是空白的——这条是我走查界面时看见的，**只有界面能证明"能用"**。
5. 刷新后历史对话消失：列表接口 `view()` 漏了 `transcript` 字段。教训是同一实体在两个接口各拼一次视图必然漂移。
6. 新建建档表单预填了某位演示老人的生日（写死的初值），已改为空；演示老人的 `chronic_json`/`allergy_json` 曾一律写成 `[]`，而这两项是风险评分与用药冲突的输入——"看起来填了、其实是空的"比没填更危险。
7. `POST /ai/ping` 在未配置 Key 时直接抛异常返回 500，把"通道没开"说成了"服务出错"；改为返回 200 + `configured:false` + hint，验收脚本据此把模型相关断言标 SKIP（40 通过 / 2 跳过 / 0 失败）。
8. **降级路径没有闭环**：界面提示"请手工填写结构化档案"，却没有输入控件与保存接口——说"请人填"就得同时给表单、给接口、给保存后的状态。
9. 抽取结果的字段名在后端叫 `data`、前端声明成 `structured`，TypeScript 不报错、页面"安静地显示空"，回传的药单一度变成 0 条。
10. 人工保存用整份覆盖，没提交的字段被当成空值写回（改一项药、清掉整张药单）；改为合并语义后复测通过。置信度也没清，人工改过的档案还挂着模型的"低置信度"提示。
11. 中文短语按空格拆词，"高血压 3 级"被拆成三条诊断；分隔符改为只认中文/英文标点与换行。

界面走查的截图见 `docs/screenshots/`，八个页面按角色顺序排列。

## 11. AI 协作过程（"全程用 AI"的证据）

开发过程按"一轮对话 = 一个模块"推进，每轮在 `docs/ai-log/` 留一篇日志：
`D0 脚手架`、`D1 交接环`、`D2 执行环`、`D3 随访环`、`D4 模型接通与复盘环`、`D5 前端与演示数据`、`D6 角色边界与验收脚本`、`D7 界面走查`、`D8 建档表单校验`、`D9 人工填写链路`、`D10 系统设置与模型接入`。
每篇包含：**这一轮输入的意图 / AI 参与边界 / 产出清单 / 踩坑与修法 / 验证记录 / 教训**。

分工是固定的一套：我先写清这一轮要做什么、拿什么算做完了，AI 出实现并跑自测，
我按同样口径复核，不过关就退回重做；修法也一并落进当轮日志。

落到具体环节：

| 环节 | 我做的 | AI 做的 |
|---|---|---|
| 定范围 | 按 A1–A10 排优先级，「从零造轮子」的方案直接否掉 | 列候选方案与工期估算 |
| 定规则 | 判 84 岁独居 + 髋部术后 + 5 种药只值 5 分不合理，要求补维度 | 加 `HOME_GAP +2`，不改权重体系 |
| 实现 | 定验收口径（断言全绿 ≠ 页面可用） | 写代码、跑单测、跑 `api-test.mjs` |
| 排查 | 走查界面，发现随访气泡只有标签没有内容 | 按真实 JSON 定位字段名，修 `toTurn()` |
| 收尾 | 批准一次提权构建，界面由我验收 | 写文档、日志、演示脚本 |

日志里有具体的、可核对的细节，而不是"我用 AI 生成了代码"这种表述。例如：
- 规则修订的理由（为什么加 `HOME_GAP +2`，为什么 `falls.happened` 只认"摔/跌"）；
- 缺陷根因链（五步，从 `LocalDate` 序列化到 NPE 到静默回退）；
- 每个数字的出处（4/MEDIUM、7/HIGH、1/LOW；42 条与 56 条任务；9 未关闭预警、7 待处置工单）。

## 12. 局限与后续

- **未做真机适老化测试**：当前只有大字号/高对比开关，缺少真实老年用户的可用性验证。
- **评价集偏小**：8 个场景各跑 1–3 次，未做系统性评测（计划：30 条脱敏出院小结 + 30 条随访对话，人工标注比对）。
- **再入院数据缺失**：30 天结局目前用系统内指标代理（预警次数、完成率、红旗数），未接入区域卫生平台。
- **照片判读未接视觉模型**：当前只排队目视，避免在无标注数据时引入误判风险。
- **多租户与账号体系**：演示环境为单机构，生产化需要机构隔离与更细的权限矩阵。
